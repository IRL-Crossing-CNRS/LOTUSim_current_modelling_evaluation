# Analysis — from recorded runs to the reported tables

Every number reported for the model-as-environment evaluation is computed
here, from `../results/` and `../experiment/`. Nothing in this folder
simulates anything, so the whole analysis can be re-run on a machine with no
simulator installed.

## Running it

```bash
export LOTUSIM_EVAL_ROOT=<this repository>   # read the released runs
export SCENARIO_WS=<parent of LOTUSim-generic-scenario>

python3 analysis/make_tables.py       # summary tables, aggregated by regime
python3 analysis/energy_table.py      # per-date energy: level and departures
python3 analysis/per_date_tables.py   # per-date tables (--write updates the README)
```

Each script takes an optional list of dates; with none, it uses every date
that has a complete set of twelve runs.

- **`LOTUSIM_EVAL_ROOT`** points the readers at this repository's
  `results/`, `experiment/scenarios/` and `experiment/vehicle_assets/`.
  Leave it unset to read a local simulator checkout instead — that is the
  mode to use right after simulating dates of your own (`SCENARIO_WS` and
  `LOTUSIM_WS` then say where those checkouts are).
- **`SCENARIO_WS`** is needed even in released-data mode, for one reason:
  the field-accuracy columns evaluate the fitted Ekman model, and that model
  is taken from `LOTUSim-generic-scenario`'s `src/lotusim_sdk` rather than
  copied here, so it cannot silently drift from the model the simulation
  applied. A clone is enough — nothing is built and ROS is not needed, since
  the module is loaded straight from its file. `LOTUSIM_SDK_PATH` points at
  `src/lotusim_sdk` directly if the checkout is not under `SCENARIO_WS`.

SciPy is the only third-party dependency (the sign, Wilcoxon and Spearman
tests).

## What each script computes

**`common.py`** — everything that reads a run, a fit or a vehicle asset, and
every metric definition. The three scripts share it so they cannot drift
apart: a per-date table and an aggregate computed from different definitions
would disagree for no stated reason.

**`make_tables.py`** — the two summary tables, aggregated by regime
(`resolved` / `collapsed`: whether the fitted wind-driven layer reaches the
depths the vehicle flies). Field accuracy is Ekman's RMSE against the
measured 0-150 m profile versus the single constant baseline's; the
closed-loop margin is the geometric-mean ratio `eps_GM/eps_Ekman` with a
binomial sign test, so the result carries a p-value rather than a win count.
Writes `regimes.json`, the date lists everything else keys on.

**`energy_table.py`** — per-date energy: the reference level and each
model's *signed* departure from it. Signed on purpose: the side matters
operationally, since a simulator that overestimates consumption sizes a
battery conservatively while one that underestimates it plans a mission the
vehicle cannot finish. Writes `energy_table.json`.

**`per_date_tables.py`** — the three per-date tables in
[../experiment/README.md](../experiment/README.md): deployed parameters,
field accuracy, and closed-loop ratios with energy. `--write` splices them
between that file's markers, so they are regenerated rather than edited by
hand after dates are added.

## Data files here

- `regimes.json` — the `resolved` / `collapsed` / `all` date lists, plus the
  per-date field-accuracy and energy records behind them. Regenerated by
  `make_tables.py`.
- `energy_table.json` — per-date energy rows. Regenerated by
  `energy_table.py`.
- `wind_beaufort.json` — each date's measured 10 m wind, as a Beaufort
  number. Measured from the Copernicus wind product and independent of the
  current fit, which is what lets a date's conditions be stated without
  reference to any model's parameters. Input, not output: adding a date
  means adding its row (see
  [../experiment/scripts/README.md](../experiment/scripts/README.md) for the
  screening step that measures it).
