# LOTUSim experimentation

Data and tooling for the closed-loop BlueROV2 comparison: does the current
model change vehicle behaviour under PID control? Nothing in this folder
runs a simulation by itself — it's copied into a `LOTUSim`/
`LOTUSim-generic-scenario` checkout, which does the actual simulating. See
the top-level README's "Reproducing results" for the copy/run steps, and
the note there on how paths here map onto that checkout.

- [experiment/](experiment/README.md) — scenario JSONs
  (`scenarios/`), the generators/drivers (`scripts/`), and the per-date
  fitted vehicle YAMLs (`vehicle_assets/`)
- results/ — recorded runs, aggregates, figures (output of
  `experiment/scripts/`)

The previous version of this study is preserved on the
`appendix/superseded-experiments` branch — its own `models/`, `configs/`,
`scripts/`, `results/` and `docs/` — but is not used to reproduce the current
results above. That branch's README explains what it asked and why it was
superseded.

## LOTUSim concepts used below, in plain terms

The READMEs in this folder assume the vocabulary LOTUSim itself uses. If
you've never touched LOTUSim, LOTUSim-generic-scenario or xdyn, here's the
minimum needed to follow them — not a substitute for those projects' own
documentation, just enough to stop being surprised by the terms.

- **Scenario** — one experiment run, declared as a single JSON file
  (`experiment/scenarios/*.json`): which vehicle model, which
  world/environment, and one or more **agents**.
- **Agent** — one simulated vehicle instance in a scenario (here, always one
  BlueROV2). A scenario can run several agents at once — the station-keeping
  scenarios run three, one per depth, in the same current field
  simultaneously.
- **Task** — one unit of behaviour an agent runs; an agent's **mission** is
  an ordered list of tasks. The tasks used here: a **Guidance** task (decides
  where the vehicle should currently be — hold point or path), a **Control**
  task (turns tracking error into forces/torques, PID here), an
  **Allocation** task (turns those forces/torques into six individual
  thruster commands), and a `bluerov_metrics_recorder` task (subscribes
  only, writes the CSV/JSON this repo's `results/` holds). This
  Guidance → Control → Allocation split is the **GNC decomposition**; it's
  specified in `LOTUSim-generic-scenario`'s
  `GNC_MODULAR_ARCHITECTURE.md`, not in this repo.
- **`lotusim_sdk`** — the shared Python library, in
  `LOTUSim-generic-scenario`, that the above tasks and this repo's
  feedforward controller (`lotusim_sdk/control/current_feedforward.py`) are
  built from. Not part of this repo; it's what gets imported once `scripts/`
  is copied into a `LOTUSim-generic-scenario` checkout.
- **`scenario_launch.sh`** and its stop convention — the
  `LOTUSim-generic-scenario` executable that starts a scenario. None of
  these scenarios has a scripted end condition (station-keeping holds
  forever, a transect keeps running once arrived), so you stop it yourself:
  Ctrl+C once the metrics recorder task logs "ENOUGH DATA" for every agent
  (meaning enough post-settle samples have accumulated). A hard kill instead
  of Ctrl+C can skip writing the final `_summary.json`.
- **xdyn, and "compiled" current models** — xdyn is the physics/dynamics
  backend (`LOTUSim-Xdyn`) that actually integrates the vehicle's equations
  of motion each step. Some current models are implemented directly in
  xdyn's C++ (`environment_models/EkmanUWCurrentModel.cpp`) and selected
  through the **vehicle YAML**'s `environment models:` block — not through
  the scenario JSON. That's why an Ekman condition needs its own vehicle
  YAML per date
  (`experiment/vehicle_assets/BlueROV2_current_fitted_ekman_<date>.yml`),
  while the Gauss-Markov current is generated by a separate host-side
  physics plugin and configured entirely from the scenario JSON
  (`gauss_markov_current` block, no vehicle YAML change needed).
